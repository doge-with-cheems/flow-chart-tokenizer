# 流程图 → 软件构建映射

编译逻辑 MD 时，最大的风险不是“漏了一个步骤”，而是把图翻译成了一段**不能施工的散文**。这份参考给出映射规则和拆分粒度。

## 1. 元素映射

| 图中元素 | 代码落点 | 验收证据 |
| --- | --- | --- |
| start | `main()`、CLI 入口、HTTP 路由、事件订阅、按钮回调 | 入口能被触发 |
| process | 一个函数/方法/脚本步骤 | 单元测试、命令退出码 |
| decision | `if`、`match`、状态迁移、参数校验、守卫 | 两条分支各跑一次 |
| io | UI 控件、剪贴板、文件读写、HTTP 客户端、消息队列 | 输入能进、输出能观察 |
| database | schema、model、repository、迁移脚本 | 建表成功、增删查改通过 |
| subprocess | 独立模块/service/worker；主流程写“调用 SP1” | 模块可单独导入/启动 |
| parallel | 线程、协程、进程池、队列；fork/join | 并发跑一遍，无竞态 |
| loop | 重试、轮询、消费者、分页 | 失败重试与退出条件都验证 |
| end | 退出码、HTTP 响应、持久化终态、通知 | 终态可断言 |
| note | 约束、兼容性说明、配置默认值 | 写进 §9 或代码注释 |

## 2. 拆分粒度

一个步骤应该满足：

- **一个落点**：主要改 1 个文件，最多 2–3 个强相关文件。
- **一个验收**：一条命令或一个可观察现象就能判断过没过。
- **一个副作用**：写库、发网络请求、改 UI、发通知是不同副作用，不合并。
- **可回退**：做完这步，下一步失败时不需要推倒重来。

反例：

- ❌ “实现后端” → 太粗，无法验收。
- ❌ “完成登录和数据库” → 两个副作用。
- ✅ “建 `users` 表与 `UserRepository`” + “实现 `POST /login` 与密码校验”。

一个 `process` 节点如果自然包含多个副作用，拆成 `S3a/S3b` 子步骤，但都标同一个 `- 节点: Nx`。

## 3. 按图形态选架构

### 3.1 用户交互流（UI → 判断 → 动作）

图中出现“点击/选择/弹出/关闭”时：

- 每个 `io` 节点 → 一个界面状态或事件处理器。
- 每个 `decision` → 一个状态迁移或守卫。
- 需要一个显式状态机：`idle → capturing → judging → answering → done/closed`。
- 取消/关闭路径必须和成功路径一样有步骤。
- 验收用“操作 → 现象”，例如“选中文字右键 → 面板出现”。

### 3.2 数据处理流（输入 → 转换 → 存储）

- `io` 入口 → source adapter，定义输入契约。
- `process` → transform 函数，输入输出都是纯数据。
- `database` → sink/repository，保证幂等。
- `decision` → 数据质量校验（空值、类型、重复、超时）。
- 必须写断点续跑与重复执行策略。
- 验收用“给定样例输入 → 期望输出/表行数”。

### 3.3 服务编排流（调用外部 API）

- 每个外部调用 → 一个 client 方法，带超时、重试、错误映射。
- `decision` → 状态码/业务错误分支。
- 密钥从环境变量或配置读，不写进代码。
- 验收用假服务（fake/mock）跑成功、失败、超时三条路径。

### 3.4 状态机流（订单/任务/审批）

- 节点 → 状态，边 → 迁移事件。
- 先写状态枚举与迁移表，再写处理器。
- 每个状态要知道“允许哪些事件、拒绝哪些事件”。
- 验收用迁移矩阵：合法迁移通过，非法迁移被拒。

### 3.5 CI / 发布 / 运维流

- `process` → 脚本步骤或 pipeline job。
- `decision` → 门禁（测试、审批、版本检查）。
- 每个副作用（打 tag、推 registry、部署、通知）单独成步。
- 必须写失败回滚和人工介入点。
- 验收用“dry-run 输出”或“预发环境结果”，不要直接在生产验。

## 4. 推荐施工顺序

即使图的主路径不是这个顺序，编译时也优先按下面顺序重排**实现顺序**（保持图的语义不变）：

1. **骨架**：目录、入口、依赖、配置。
2. **数据契约**：类型、schema、接口定义。
3. **核心纯逻辑**：不依赖 UI/网络的函数。
4. **外部边界**：文件、数据库、HTTP、剪贴板、UI。
5. **主路径串起来**：从 start 到第一个 end 能跑通。
6. **分支与异常**：失败、取消、超时、空输入。
7. **并发/循环**：如果图里有。
8. **总验收**：§7 的 G 门槛。
9. **打包/交付**：安装包、文档、示例配置。

图的节点编号不变，只调整 S 的顺序；在 §1 执行契约里说明“实现顺序按依赖重排，执行顺序仍按 S”。

## 5. 任务类型判定

| 图的特征 | 任务类型 |
| --- | --- |
| 有 UI/交互节点，终态是一个可用工具 | `build-software` |
| 在已有仓库里加节点对应的功能 | `extend-software` |
| 节点围绕“复现 → 定位 → 修复 → 回归” | `fix-software` |
| 节点围绕“基线测试 → 改结构 → 回归” | `refactor-software` |
| 节点是构建、测试、发布、部署、回滚 | `build-automation` |
| 节点是采集、清洗、转换、入库、调度 | `build-data-pipeline` |
| 节点是写作、排版、审校、导出 | `build-doc` |
| 节点只做检查、审计、验收，不产生功能 | `verify-only` |

拿不准时默认 `build-software`，在 §9 写“任务类型为推断，可按用户要求切换”。

## 6. 验收写法

好的验收：

- `python -m pytest tests/test_store.py -q` 退出码 0。
- `curl -s localhost:8000/health` 返回 `{"ok":true}`。
- 选中文字右键，面板在 300ms 内出现，且原生菜单不出现。
- 空白处右键，原生菜单出现，程序不弹面板。
- 同一输入跑两次，数据库行数不增加（幂等）。

坏的验收：

- “功能正常”。
- “界面友好”。
- “代码没问题”。
- “人工确认一下”（除非确实无法自动化，并说明原因）。

## 7. 常见错误

| 错误 | 后果 | 修正 |
| --- | --- | --- |
| 一个节点写成“实现整个模块” | 无法验收、无法定位失败 | 按副作用拆子步骤 |
| 把判断写成处理 | 分支丢失 | 单独 `decision` 步骤，至少 2 条出边 |
| 把并行写成顺序 | 性能/语义都错 | 标 `P1`，写 fork/join |
| 省略失败/取消路径 | 上线后卡死 | §5 必须覆盖所有 `no/error` 边 |
| 循环没有退出条件 | 死循环 | 写最大次数和超限去向 |
| 合并不同副作用 | 回滚困难 | 打 tag / 发布 / 通知分开 |
| 用“应该会”代替实测 | 执行 agent 走错分支 | 判断步骤必须给可观测条件 |
| 逻辑 MD 与 flow-json 不一致 | 校验失败、图论错误 | 以正文为准同步 flow-json |
